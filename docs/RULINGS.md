Evidence: plan `business/ebda/plans/2026-10-26-ebda-foundation.md` section 2 compared a git-tag dependency (private clone credentials in every workflow, one package only), GitHub Packages (PAT and 500 MB / 1 GB quota failure modes on a $0 plan) and a template repo (a copy loses its link); the vendored copy needs zero network and zero auth. Ruling FDN-PHONE-1 - Phone normalisation is the WhatsApp PHONE-2 version (`normaliseE164`, a national number is +20 only when it is a valid Egyptian number), seeded from ebda-whatsapp commit 3f7878d with `vectors/phone.json` and `vectors/buyer-key.json` byte-identical and sha256-pinned. The Store's phone storage format is NOT changed by the foundation; `buyerKey` input always goes through `normaliseE164`, and a storage-format change is a separate data PR. Evidence: CODE-10 (a wrong E.164 gives a wrong buyerKey and a broken consent match across the suite); vectors f1d99cad... (phone) and 00c47c95... (buyer-key). Note: commit 3f7878d is on branch `fix/phone2-vectors` of ebda-whatsapp and was not yet on its `main` when this was seeded (main 38db683). Cost if wrong: a Store customer whose stored phone differs from the E.164 form gets a different buyerKey until the data PR lands, so cross-product consent matching misses them.

Ruling FDN-TEXT-1 - The Store Arabic fold is canonical: `foldArabic` is `normalizeArabicSearch` byte for byte (no Unicode normalize, no locale lowercasing, so the SQL twin `public.ebda_ar_norm` can match it; Ruling SEARCH-2). `indexTokens` is the fold plus punctuation to space. The WhatsApp product re-indexes onto it (plan step F7). Evidence: SQL twin verified present on ebda-store origin/main 656d5d6fc (migration 20261019000100_search_normalisation and later); the WhatsApp normaliser used NFKC and did not fold ئ ؤ ک. Cost if wrong: WhatsApp search quality for those letters is lower until the re-index, and a second fold would split search results across products.
