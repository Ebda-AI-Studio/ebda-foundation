# Blast-Radius PR Reviewer

`ops/blast-radius.sh` — part of the Whisky AI OS read-only analysis tier.

## What it does

Given a PR, it asks: *"which other files in this repo could break because of this change?"*

1. Fetches changed files from GitHub (`gh pr diff --name-only`).
2. Loads the repo's `graphify-out/graph.json` (the dependency knowledge graph).
3. Traverses the reverse-dependency graph (BFS) to find every file that directly or transitively imports/calls/references any changed file.
4. Assigns a risk level and posts a single Telegram digest via `ops/notify.sh`.

### Risk levels

| Level | Condition |
|---|---|
| NONE | Zero graph-reachable dependents |
| LOW | 1–5 dependent files |
| MEDIUM | 6–20 dependent files |
| HIGH | 21–60 dependent files |
| MAXIMUM | >60 dependents, OR any changed file under `packages/shared` or `packages/database` (these ripple to all apps regardless of graph coverage) |

MAXIMUM is always flagged for `packages/shared` and `packages/database` changes because they are the shared kernel — even if the graph doesn't yet have edges for a brand-new file, the structural risk is real.

## Usage

```bash
# Standard: by PR number
DRY_RUN=1 ops/blast-radius.sh force-website-builder 94

# Ref-based (for CI use later): base..head + optional repo root path
DRY_RUN=1 ops/blast-radius.sh force-website-builder main..feat/my-branch /path/to/repo

# Real run (sends Telegram alert when risk > NONE)
ops/blast-radius.sh force-website-builder 94
```

### Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `DRY_RUN` | `0` | `1` = print the Telegram message instead of sending it |
| `GRAPH_ROOT` | auto-detected | Path to the directory containing `graphify-out/graph.json` |
| `BLAST_TOP_N` | `20` | Max dependent files shown in report |
| `GH_USER` | the org in `OS_REPO_SLUG` (os.env) | GitHub username/org owning the repos |

### Graceful degradation

If `graphify-out/graph.json` is absent for a repo, the script exits 0 with a warning — CI is never blocked by a missing graph. Run `graphify .` in the repo once to generate the graph.

## Prerequisites

- `gh` CLI authenticated
- `python3` on PATH
- `graphify-out/graph.json` present in the target repo (generated by `graphify .`)
- Telegram creds at `~/.whisky-whoop-telegram.env` (for live alerts; `DRY_RUN=1` bypasses this)

## How the graph is traversed

The `graphify-out/graph.json` stores nodes (code symbols + file-level entries) and links with relation types: `imports_from`, `imports`, `calls`, `references`, `contains`. The script uses the first four as dependency signals, then does a BFS over the *reverse* graph (target → source) to collect all transitive dependents. Node scores reflect how many unique nodes within a dependent file reference any changed-file node — higher score = tighter coupling.

## Limitations

- Graph coverage depends on when `graphify .` was last run. A file added after the last graph extraction will have no nodes, so its import-level dependents won't be found (but if the file is in `packages/shared/packages/database`, MAXIMUM risk is still triggered structurally).
- The graph captures static import/call relationships. Dynamic requires, monkey-patching, and runtime DI are invisible to it.
- Test files often score highly (they import many things) — this is correct: a shared utility change should trigger re-running the tests that exercise it.
