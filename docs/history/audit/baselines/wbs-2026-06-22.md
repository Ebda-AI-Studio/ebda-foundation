## VERDICT

**Partial regression from 2026-06-08.** The RLS cutover (migration `20260608210000_rls_force_cutover`) shipped correctly and the webhook P0 was fixed, but the cutover broke every non-tenantContext data route (`/api/campaigns`, `/api/messages`, `/api/conversations`, `/api/templates`, `/api/media`) — reads return 0 rows, writes are rejected by FORCE RLS — and Task 4 of the remediation plan (`docs/superpowers/plans/2026-06-13-rls-tenant-context-data-routes.md`) is incomplete as of HEAD. Additionally the CI audit gate is currently broken by 5 HIGH-severity prod-scope vulns introduced transitively since lockfile refresh (`form-data` CRLF via axios, `ws` DoS, `tmp` path traversal via exceljs, `engine.io`, `socket.io-adapter`). These two issues together mean WBS is **partially production-broken right now**: login/admin works, but campaign/contact/conversation/template reads/sends are silently empty.

## Top 3 Findings (P0/P1)

### Finding 1 — ACTIVE OUTAGE: campaigns/messages/conversations/templates return 0 rows under FORCE RLS
**Location:** `backend/server.js:265-285` (route mounts) + `routes/campaigns.js`, `routes/messages.js`, `routes/conversations.js`, `routes/templates.js` (0 calls to `runInTenantContext`/`withRlsBypass`/`establishTenantScope`)
**What:** Since the FORCE RLS cutover (`20260608210000`), these 5 routes run as `wbs_app` with no `app.current_client_id` GUC set. FORCE RLS evaluates to DENY for every row. Reads silently return 0 rows; writes throw `WITH CHECK violation` (swallowed by Express error handler). The ALS-routing proxy falls through to the base client when no tenant tx is active — which is always the case for these routes.
**Blast radius:** Every campaign list/send/retry, every WhatsApp message send, every inbox conversation load, and every template list is broken for every client. Verified structurally: the plan doc (`2026-06-13-rls-tenant-context-data-routes.md`) lists Task 4 as incomplete checkboxes.
**Fix:** Implement Task 4 — per-operation `runInTenantContext(clientId, ...)` or `withRlsBypass(...)` scopes on the GET handlers of these routes; structure I/O handlers as read-in-context → close → Meta call → write-in-context (never hold tx across network I/O).

### Finding 2 — CI GATE BROKEN: 5 HIGH prod-scope vulns, audit exits non-zero
**Location:** `backend/package.json` (transitive via `axios`, `socket.io`, `exceljs`); `pr-validation.yml:200-205`
**What:** `npm audit --audit-level=low --omit=dev` in `backend/` exits 1 with 5 HIGH CVEs (form-data CRLF, ws DoS, tmp path traversal CVSS 8.2, engine.io, socket.io-adapter). The CI step uses `set -e` and fails hard. All PRs since the lockfile refresh (`1a3baeba`, 2026-06-09+) have been merging against a broken security gate. The `form-data` CRLF injection (GHSA-hmw2-7cc7-3qxx) is in a direct prod dep (`axios`).
**Blast radius:** Security gate is non-functional; new vulnerabilities can merge undetected. The `form-data` CRLF injection could be exploited via any multipart request using axios.
**Fix:** Add `overrides: { "form-data": ">=4.0.6", "ws": ">=8.21.0", "tmp": ">=0.2.7" }` to `backend/package.json` and `frontend/package.json`; upgrade `socket.io` to `>=4.8.4`; run `npm install --package-lock-only` with the CI npm version (10.8.2); restore gate to green.

### Finding 3 — `message_status_events` Prisma model absent — event log silently never writes
**Location:** `backend/prisma/schema.prisma` (model missing); `backend/src/services/whatsapp.js:1424`
**What:** The DB table `message_status_events` exists (migration `20260530175523`) and the code calls `this._db().message_status_events.create(...)` at `whatsapp.js:1424`. But the Prisma schema has no `model message_status_events` — so `prisma.message_status_events` is `undefined` at runtime. The `TypeError` is caught and logged as a warning (`whatsapp.js:1434`) and never surfaced. The append-only delivery-receipt audit log contains zero rows in production despite 2+ weeks of traffic.
**Blast radius:** The entire delivery-status audit trail (rank-guard evidence, applied=false out-of-order receipts) is unrecoverable for historical traffic. Any future debuging of message delivery requires it.
**Fix:** Add `model message_status_events { ... }` to `schema.prisma` (introspect from the existing table or hand-author the 7 columns) + run `prisma generate` + add unique constraint `@@unique([whatsapp_message_id, to_status])` for idempotency.
