### Remaining gaps

**1. (High) mfa.routes — no Zod validation on 4 POST handlers**
`apps/api/src/routes/mfa.routes.ts` (227 lines, 0 Zod imports). The 4 POST handlers (`/enroll/begin`, `/enroll/verify`, `/verify`, `/disable`) all manually destructure `req.body` with type assertions (`const { code } = req.body as { code?: string }`). No schema parse/safeParse. An attacker who sends a 10 MB `code` field or a non-string value hits the underlying logic without structural validation. Prior gap: noted in 2026-06-08 baseline — NOT FIXED.  
Fix: add `const bodySchema = z.object({ code: z.string().length(6).regex(/^\d+$/) })` and `.safeParse()` at the top of each handler.

**2. (High) bulk.service + newsletter CSV exports — no formula injection guard**
`apps/api/src/services/bulk.service.ts:1059-1064` `escapeCSV()` only wraps in quotes if the field contains `,`, `"`, or `\n` — it does NOT strip or prefix formula triggers (`=`, `+`, `-`, `@`). A merchant whose product is named `=cmd|'/c calc'!D7` (or whose customer's name starts with `=`) can phish the merchant who opens the CSV in Excel.  
`apps/api/src/routes/newsletter.routes.ts:101-109` `escapeCsv()` has the same shape — quoting only, no formula guard.  
`admin.routes.ts:1280-1295` `csvField()` DOES strip formula triggers (prepends `\t`). That function was never extracted to shared.  
Fix: extract `csvField()` from `admin.routes.ts` into `@force/shared/csv-utils.ts`, replace `escapeCSV()/escapeCsv()` in bulk + newsletter with the shared version.

**3. (Medium) Admin content preview — dangerouslySetInnerHTML with client-rendered HTML**
`apps/admin/src/app/stores/[id]/content/[slug]/page.tsx:550` renders `<div dangerouslySetInnerHTML={{ __html: preview }} />` where `preview` is the output of `renderBlocksToHtml()` replicated CLIENT-SIDE at line 71. The client-side replica uses `escapeHtml` and `safeUrl`, matching the server-side implementation. Risk is client-side drift: if the client-side replica diverges from `apps/api/src/services/pages.service.ts`, the preview could accept values the server would reject. Current parity verified but no automated cross-check enforces it.  
Blast radius: admin users only (authenticated). Not a Critical, but warrants a test that compares both renderers on the same input set.

**4. (Low) authLimiter max=15 still above rubric's 5/15min**
`apps/api/src/middleware/security.ts:264` — the code comment now explains the deliberate increase (prevents rate-limit from conflicting with account-lockout-at-5). Rubric says 5; current is 15. Intentional as of 2026-06-22 but not documented in DEPLOYMENT.md as a security design decision.

### Remaining gaps

**1. (Critical) store_staff + 8 older tables: ENABLE but no FORCE RLS**
`migrations/20260615010000_add_staff_role_and_store_staff/migration.sql:39` — `store_staff` has `ENABLE ROW LEVEL SECURITY` but NO `FORCE ROW LEVEL SECURITY`. Absent from `20260616210000_store_staff_write_policies` too. The `neondb_owner` superuser (which local dev connects as) can bypass RLS on store_staff without FORCE. Sibling: `20260522000000_rls_for_8_missing_tables/migration.sql` enables RLS on `blog_posts`, `store_faqs`, `store_howtos`, `product_faqs`, `ai_recommendation`, `bulk_ai_jobs`, `ai_usage` — none have FORCE statements.  
Fix: add a new migration with `ALTER TABLE store_staff FORCE ROW LEVEL SECURITY;` and the 7 missing tables from the 2022 batch.

**2. (Critical) IS-NULL-escape policy shape on ~120 policy rows**
`grep "IS NULL" migrations/ --include="*.sql" | wc -l` = 120. The "IS NULL = no tenant context = allow" escape is documented as a hazard in ADR-0001. New migrations since 2026-06-08 (barcode, locations, bank-recon, shipping-area-rates) use the explicit `current_setting('app.bypass_rls', true) = 'true'` shape, which is correct. But ~120 existing policies retain the IS-NULL shortcut — any code path that accidentally fails to set either GUC gets unfiltered reads rather than an error.  
Fix: migrate existing IS-NULL policies to explicit bypass-GUC check; add integration test asserting that force_app with no GUC set gets empty result (not all rows).

**3. (Critical-shape) Boot-time role assertion still absent**
`apps/api/src/index.ts` — no `SELECT current_user` check at startup to verify the process connects as `force_app` (not `neondb_owner`). Noted in 2026-06-08 baseline, not implemented.

**1. (Medium) Affiliate Decimal fields: schema Decimal ↔ service Number() math**

## Cross-cutting findings

### DR contradiction: neon-snapshot.yml is ACTIVE, not retired

Global CLAUDE.md states `neon-snapshot.yml is now **disabled on every repo**`. FWB reality: `.github/workflows/neon-snapshot.yml` still exists, still triggers on `push: branches: [main]`, and creates `prod-${SHORT_SHA}` branches with pruning at 30. This contradicts the global memory AND the prior baseline note (which said "disable/delete neon-snapshot.yml + delete 3 stale prod-SHA branches" as a Medium gap that was never closed). If NEON_API_KEY is unset in Railway, the step exits 0 harmlessly — but if it IS set (which it should be for branch management), the workflow creates branches and accrues compute costs.

### Branch hygiene: 210 remote branches (was 33 in 2026-06-08 baseline)

`git branch -r | wc -l = 210`. Includes 9 `auto-fix/*` branches, `staging`, `test/regression-checkout-payment`, `plan/*`, `perf/*`, `hotfix/*` (2), `chore/*` (4), `ci/*` (6), 100+ `feat/*` and `fix/*` worktree branches. Many are likely merged-and-forgotten worktrees. This bloat means gitleaks scans `fetch-depth: 0` against the full history but the surface for stale credentials is high.

### Gitleaks --config flag still absent

`.github/workflows/gitleaks.yml` runs `gitleaks detect --source . --redact --verbose --exit-code 1` — no `--config .gitleaks.toml`. The `.gitleaks.toml` allowlist exists but is silently ignored by the workflow. Prior baseline gap still open.
