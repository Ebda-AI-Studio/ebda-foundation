# Standard: one Arabic search

**Rule.** Search text and queries go through `foldArabic` / `indexTokens` / `searchTokens` (`@ebda/foundation/text`); search boxes use `useLiveSearch` + `useListboxNav` + `highlightSegments` (`@ebda/foundation/web/search`): from 1 character, 150 ms debounce, the superseded request aborted, results only for the query in the box, ARIA combobox. A product keeps its own fetcher, list rendering and i18n strings. Behaviour is pinned by `vectors/arabic.json` (fold) and `vectors/arabic-search.json` (does query X find text Y).

**Two folds (Ruling F7-HAMZA-2).** A query word matches a document word when they agree under fold B OR under fold A.
- **Fold B** = the original Store fold: alef forms to ا; ى ی ئ to ي; ؤ to و; ة to ه; Persian ک to ك; tashkeel, dagger alef, tatweel removed; ASCII lower; Arabic-Indic and Persian digits to 0-9; whitespace collapsed. `foldArabic`, `indexTokens`, `searchTokens`. Unchanged; its SQL twin `public.ebda_ar_norm` is unchanged. Typed ي for ئ (`سايل` = `سائل`, `رايع` = `رائع`) is B's equivalence.
- **Fold A** = the hamza fold: NFKC first (pasted lam-alef ligature, presentation forms, fullwidth digits and letters, thin and ideographic spaces become the typed letters), then B's table except that ء ئ ؤ all become و, then a run of و collapses. `foldArabicHamza`, `indexTokensHamza`, `searchTokensHamza`. `مسئول` = `مسؤول`; `سؤال` = `سوال` = `سئوال`; `سائل` = `ساءل`; `حذاء` finds `حذائي`. SQL twin: `public.ebda_ar_norm_h` (Store migration 20261123000100_search_fold_hamza); `normalize(t, NFKC)` is IMMUTABLE in Postgres 13+ (verified on 17.11).
- Not transitive on purpose (`مسيول` ~ `مسئول` ~ `مسؤول`, but `مسيول` is not `مسؤول`), `سائل` is not `سال`. `vectors/arabic.json` (35 original vectors) is the B no-regression set; `vectors/arabic-hamza.json` pins A, the same-term pairs (either fold) and the different-term pairs (neither).
- Use: index text with `indexTextBoth` (one text per row, B then A when they differ) or two columns; query each typed word through `searchWordPairs` (`[b, a]`, or `[t]` when equal, then tried against both) and OR the two forms; highlight with `highlightSegments`.

**Ebda Chat migration (flag-gated, do not run before the foundation is re-vendored).**
1. Flag: the platform var `SEARCH_FOLD` (`'v2'` = on; unset or anything else = off, the default). Off: `normaliseText` builds and queries `contacts_fts` / `messages_fts` exactly as today.
2. State per workspace: `store_state.search_fold = 'v2'` marks a workspace whose indexes were built with `indexTextBoth` (B tokens, then A tokens when they differ). Index writes (`indexContactName`, `indexMessage`) and query words (`/conversations?q`, `/search`, campaign contact search) all read that ONE marker (`searchFoldOf(sql)`), so index and query can never disagree.
3. Re-index: when a DO wakes and `env.SEARCH_FOLD === 'v2'` differs from its marker, `syncSearchFold` writes the marker and runs `rebuildFts` (contacts + messages) in ONE `transactionSync`: a workspace is never half-way, and a crash rolls both back. Cost: one pass over `contacts` and `messages.preview` of that workspace (the same pass a backup restore already does); a very large workspace pays it once, on first wake after the flip. No numbered DO migration (FTS5 content is derived data). If the controller prefers a numbered migration, it takes the next free version from the Chat registry.
4. Rollback = unset the flag: the next wake deletes the marker and rebuilds with `normaliseText`.
5. Verify per workspace after the flip: `SELECT value FROM store_state WHERE key='search_fold'` is `v2`; `count(*)` of `contacts_fts` equals contacts with a name; `مسؤول` finds `مسئول`; `سوال` finds `سؤال` and `سئوال`; `كوتشي` finds `کوتشی`; `سايل` still finds `سائل`. Behaviour changes versus the old fold are listed in the Chat PR. Query words are matched as `("b"* OR "a"*)` per word.
