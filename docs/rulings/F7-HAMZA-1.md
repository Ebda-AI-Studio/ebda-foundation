# F7-HAMZA-1

Ruling F7-HAMZA-1 - The canonical Arabic search fold unifies hamza carriers and runs Unicode NFKC first (controller ruling 2026-11-23, amends FDN-TEXT-1 and SEARCH-2). Egyptian shoppers type `مسئول` and `مسؤول` interchangeably, so ء and ئ are deleted, ؤ maps to و and a run of و collapses to one و (`مسئول` = `مسؤول`, `سؤال` = `سوال` = `سئوال`, `سائل` = `ساءل`); NFKC runs before the fold so pasted compatibility forms (lam-alef ligature, Arabic presentation forms, fullwidth digits and letters) still meet the typed letters. SEARCH-2's premise that Postgres cannot reproduce NFKC immutably was checked and is wrong: `normalize(text, NFKC)` is `provolatile = 'i'` on PostgreSQL 17.11 (it needs a UTF8 database, which Neon is). Applies to the TS fold, the SQL twin `ebda_ar_norm` (Store migration 20261123000100_search_fold_hamza, with a REINDEX of every index built on it) and the shared vectors in one release. Evidence: `vectors/arabic.json` (`equivalent`, `distinct`, 52+ cases) and `vectors/arabic-search.json`. Cost if wrong: distinct words that differ only by a hamza seat or a doubled و (`سائل` and `سال`) now find each other, which costs a little precision; ئ no longer folds to ي so a query typed with ي instead of ئ (`سايل` for `سائل`) does not match; the Unicode version of NFKC in Postgres and in the JS engine can differ for characters added after the older one, which would only matter for a very new compatibility character.
