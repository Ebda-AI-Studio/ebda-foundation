# Ebda AI Studio audit pack, 2026-10-26

Source: the full read-only audit of Ebda AI Studio (company, Ebda Store, Ebda WhatsApp) run 2026-10-26 by twelve lens agents (reports in `Ebda-AI-Studio/business/ebda/audits/2026-10-26-*.md`), consolidated in `EBDA-MASTER-FINDINGS-2026-10-26.md`, whose section 7 is the lens catalogue (L01-L87) mapped at the end of this file. Ebda is Ahmad's own product, so the scenarios are quoted from the real findings. Finding ids (SEC-5, BUG-2 ...) refer to those reports.

Fleet status: every claim below ships as a graded lens in `mypovonai-learn/fleet/` (lens JSON + probe + known-bad fixture + clean twin + rubric + pack membership). Probe types: S = static source check, H = live/snapshot-fed (the `all --url/--gh` collector captures it), J = the probe only locates a candidate and a judge decides. The pack files are in `fleet/packs/`; `standard/<id>.md` mirrors each rubric in ebda-foundation.

Applied to: Ebda Store and Ebda WhatsApp (the source). Still to run: every other repo, with `mypovonai-audit all`.

## security

**webhook-persist-before-verify** (S, high; SEC-5). A webhook handler must verify the signature on the raw body before it writes the body to a table or a queue.
Scenario: Ebda payment webhooks were written to the webhook table and queued, and only then verified. Anyone who could reach the URL could fill the table and the queue with unsigned bodies.
-> Lens `webhook-persist-before-verify`. Check: Webhook handler persists or enqueues the payload before verifying its signature.
Fix: Verify the HMAC over the raw body first and return 401; persist and enqueue only after it passes.

**secret-in-url-path** (S, high; SEC-8). A shared secret must not travel in a URL path or query string, because platforms and proxies log URLs.
Scenario: Ebda's Bosta webhook secret was a path segment, so it landed in request logs of the Worker platform.
-> Lens `secret-in-url-path`. Check: Route path embeds a secret/token parameter, which is logged with the URL.
Fix: Authenticate with a header signature or a hashed token compared in constant time; strip query and path secrets from logs.

**lockout-by-victim-key** (S, high; SEC-3). A failed-login lockout counter keyed only by email/username lets anyone lock any account out on purpose.
Scenario: Five bad passwords against any address on Ebda accounts locked the real owner out; the counter never looked at the caller's IP or device.
-> Lens `lockout-by-victim-key`. Check: Failed-login lockout counter is keyed by the account identifier alone, so an attacker can lock any user out.
Fix: Key the counter by account plus caller (IP/device), back off per caller, and give the owner a recovery path that does not depend on the counter.

**csp-unsafe-inline-eval** (S, high; SEC-4). script-src with 'unsafe-inline' or 'unsafe-eval' turns the CSP into decoration against XSS.
Scenario: Ebda admin, orders and storefront shipped script-src with unsafe-inline and unsafe-eval while the admin kept its bearer token in localStorage.
-> Lens `csp-unsafe-inline-eval`. Check: script-src allows 'unsafe-inline' or 'unsafe-eval'.
Fix: Use nonces or hashes for scripts, remove eval, and keep tokens out of script-readable storage.

**bearer-in-localstorage** (S, high; SEC-4). A bearer/session token in localStorage is readable by any script that runs on the page.
Scenario: Ebda admin and orders kept the bearer token in localStorage next to a CSP that allowed inline scripts, so one XSS meant account takeover.
-> Lens `bearer-in-localstorage`. Check: Token/credential written to localStorage, readable by any script on the page.
Fix: Move the session to an httpOnly, Secure, SameSite cookie.

**headers-live** (H, medium; SEC-7, OPS-21). Every public host (not only the main site) serves HSTS, a frame policy and a CSP.
Scenario: accounts.ebda.app had no HSTS, frame or CSP headers and status.ebda.app had no HSTS, while the marketing site was fine. The check ran on one host only.
-> Lens `headers-live`. Check: Live response has no Strict-Transport-Security header. / Live response has neither X-Frame-Options nor a CSP frame-ancestors. / Live response has no Content-Security-Policy header.
Fix: Set the header block in one shared helper used by every Worker; verify each host with the snapshot probe.

**bulk-export-permission** (S+J, high; SEC-14). A route that exports all customers must require its own permission and write an audit row, not just 'is staff'.
Scenario: Any Ebda staff account could download every customer's PII in one call.
-> Lens `bulk-export-permission`. Check: Export route has no explicit permission check or audit write.
Fix: Add an export permission, check it in the handler, and audit-log each export.

**capability-url-expiry** (S+J, medium; SEC-15). A link that grants access by possession (guest order page) needs an expiry or a second factor.
Scenario: Ebda's guest order page URL showed the buyer's order and address to anyone holding the link, forever.
-> Lens `capability-url-expiry`. Check: Guest/public order token is checked without any expiry.
Fix: Add expiresAt to the token and ask for the last digits of the phone before showing PII.

**upload-trusts-declared-mime** (S, medium; SEC-12). The Content-Type a client declares is not evidence of the bytes; sniff the content before accepting or forwarding it.
Scenario: Ebda WhatsApp outbound media upload trusted the declared MIME type, so a script could be sent as an image.
-> Lens `upload-trusts-declared-mime`. Check: Allowlist check runs against the client-declared MIME type, with no byte sniffing.
Fix: Sniff magic bytes (file-type or manual signatures) and allowlist.

**og-fetch-ssrf** (S, high; SEC-6). A server-side fetch of a URL taken from the request must block private ranges and cap size and time.
Scenario: Ebda's OG image route fetched a caller-chosen URL, giving blind SSRF into the internal network.
-> Lens `og-fetch-ssrf`. Check: fetch() of a request-supplied URL with no visible host/private-range guard.
Fix: Resolve the host, deny private/link-local ranges, allowlist schemes, cap bytes and time.

**llm-moderation-fail-open** (S, critical; SEC-2). If the model call, parse or timeout fails, the content must go to a review queue, never to published.
Scenario: Ebda AI review moderation auto-published when the moderation call failed, and reviews could carry instructions aimed at the moderator.
-> Lens `llm-moderation-fail-open`. Check: catch branch of a moderation call sets approved/published. / catch block of a moderation call approves or publishes the content.
Fix: Fail closed: on any error set status pending_review and alert; approve only on an explicit, schema-valid verdict.

**prompt-injection-unfenced** (S, high; SEC-2, SEC-11). Reviews, receipts, messages and OCR text are data; put them inside a labelled untrusted block, demand a schema, and never let them carry authority.
Scenario: Ebda review text was concatenated into the moderation prompt, and the InstaPay receipt reader could be told to suppress its own warning flags.
-> Lens `prompt-injection-unfenced`. Check: User-controlled text is interpolated into a prompt string with no untrusted fence or output schema.
Fix: Wrap in <untrusted>...</untrusted>, state that nothing inside is an instruction, force a JSON schema/response_format, and compute decisions outside the model.

**dependabot-ecosystem-coverage** (S, medium; OPS-22). Automated update PRs must cover the package ecosystems the repo ships, not only workflow actions.
Scenario: Ebda's Dependabot config covered github-actions only, while production ran old and unmaintained npm dependencies.
-> Lens `dependabot-ecosystem-coverage`. Check: dependabot.yml lists github-actions but no application package ecosystem.
Fix: Add npm (and any other ecosystem in use) with a weekly schedule and grouped updates.

**cf-dns-mail-hygiene** (H, medium; OPS-17, OPS-20). A domain sending mail needs an enforcing DMARC policy (quarantine/reject) and a CAA record naming the allowed CAs; leftover provider records should be removed.
Scenario: Ebda's DMARC was p=none while platform mail went out from ebda.app, there was no CAA record, and old Resend/SES DNS records remained.
-> Lens `cf-dns-mail-hygiene`. Check: DMARC policy is p=none. / No CAA record on the apex.
Fix: Move DMARC to quarantine after monitoring, add CAA, delete unused provider records.

**pr-lane-builds-deployables** (S, high; Ebda master catalogue 2026-10-26 sec.7 L01). A security fix is not done until the pipeline that ships it is proven to build and deploy that app; the PR lane must build every deployable the deploy lane builds.
Scenario: Ebda's critical-RCE Next.js bump could not be proven: the storefront auto-deploy failed on main while the PR lane never built that app (M-001, M-004, M-016).
-> Lens `pr-lane-builds-deployables`. Check: Deploy workflow builds an app that no pull_request workflow builds.
Fix: List deployables in one place and make PR CI build each of them (path-filtered).

**bearer-staleness-undocumented** (J, low; Ebda master catalogue 2026-10-26 sec.7 L32). The bounded-stale window of a stateless bearer (how long a revoked token still works) must be documented at the check site.
Scenario: Ebda inbox/API tokens were only revocation-checked for money actions (M-135).
-> Lens `bearer-staleness-undocumented`. Check: JWT/bearer verification with no staleness or revocation note.
Fix: Add a comment/constant stating the window and the revocation path.

## privacy

**third-party-llm-egress** (S, high; SEC-9). If a tenant can set the LLM base URL or provider, buyer messages and order data leave the platform to a destination nobody reviewed.
Scenario: Ebda WhatsApp AI agent sent buyer messages and order status to a merchant-chosen third-party LLM endpoint.
-> Lens `third-party-llm-egress`. Check: LLM client baseURL/endpoint comes from tenant/merchant configuration with no provider allowlist.
Fix: Allowlist providers server-side, require a DPA flag per provider, redact PII before the call.

**legal-pending-markers** (S+J, high; DOC-3). Terms and privacy text must not ship placeholders or 'pending counsel review' clauses that look final.
Scenario: Ebda's legal text was unreviewed by counsel and the pending-review clauses were published with their markers stripped, so they read as binding terms.
-> Lens `legal-pending-markers`. Check: Legal text carries a placeholder/pending-review marker.
Fix: Gate publication of /terms and /privacy on a reviewed flag; keep markers visible until counsel signs off.

**retention-sweeper-missing** (S, medium; DB-10). Events/log/status tables need a retention window enforced by a delete job or TTL, or they grow without bound and hold PII forever.
Scenario: Ebda WhatsApp DO: message_status_events and store_orders grew without retention.
-> Lens `retention-sweeper-missing`. Check: Events/logs table is created but no retention/delete job exists.
Fix: Add a scheduled DELETE ... WHERE created_at < now() - interval, and document the window.

**privacy-promise-vs-product** (S+J, critical; DOC-1). Every deletion/closure promise in the legal pages needs a route or job that does it, within the stated time.
Scenario: Ebda's legal pages promised merchant self-serve account closure and a 90-day store deletion; the product did neither.
-> Lens `privacy-promise-vs-product`. Check: Legal text promises deletion/closure but no delete route or purge job exists in the sources.
Fix: Build the closure flow and purge job, or reword the page to what exists.

**privacy-processor-parity** (S+J, high; DOC-2, DOC-11). Every third-party processor in the dependencies must be named in the published privacy policy with its purpose and retention.
Scenario: Ebda's privacy policy omitted processors and retention that the internal data map recorded, and the approved Customer Intelligence / consent clauses were not in the published text.
-> Lens `privacy-processor-parity`. Check: A processor dependency is not named in the privacy policy.
Fix: Generate the policy's processor table from the data map; fail CI when a dependency has no row.

**platform-db-shared-tenant-bodies** (J, medium; DB-13). Raw webhook/payload bodies for every tenant in one table are a blast-radius and retention problem; purge or scope them.
Scenario: Ebda's platform D1 was one database for every tenant's directory, billing and webhook bodies.
-> Lens `platform-db-shared-tenant-bodies`. Check: Shared table stores raw bodies/payloads with no retention marker.
Fix: Store a hash plus the fields needed, expire raw bodies, and scope per tenant.

**analytics-pixel-present** (S, low; BIZ-26). Without a consent-gated analytics tag the funnel and any ad campaign are blind.
Scenario: Ebda's marketing site carried no analytics or ad pixel, so ads readiness was incomplete.
-> Lens `analytics-pixel-present`. Check: Site layout exists but no analytics tag is referenced.
Fix: Add a consent-gated analytics tag and a conversion event.

**personal-table-no-retention-row** (S+J, high; Ebda master catalogue 2026-10-26 sec.7 L34). Every table with personal columns ships with a retention row and an erasure-registry entry.
Scenario: Ebda tables holding phone, address and email had no retention row or erasure entry (M-025, M-094).
-> Lens `personal-table-no-retention-row`. Check: Table with personal columns is named in no retention/erasure document.
Fix: Add the table to the data map with a retention window and to the erasure registry; test it over the schema.

**erasure-not-replayed-on-restore** (S+J, high; Ebda master catalogue 2026-10-26 sec.7 L36). Every erasure writes a durable, replayable record that a restore re-applies, or restoring a backup resurrects erased people.
Scenario: Ebda erasures were not recorded anywhere a restore could replay (M-093).
-> Lens `erasure-not-replayed-on-restore`. Check: Erasure code exists with no tombstone/ledger/replay.
Fix: Keep an erasure ledger outside the restored database and replay it after every restore.

**r2-prefix-without-erasure** (S, medium; Ebda master catalogue 2026-10-26 sec.7 L37). Every R2 key prefix a feature writes must be in an erasure map with a delete owner or lifecycle rule.
Scenario: Ebda wrote buyer images and receipts to R2 prefixes that the erasure path never listed (M-021, M-042, M-094).
-> Lens `r2-prefix-without-erasure`. Check: R2 put() to a prefix with no erasure/lifecycle reference.
Fix: Register each prefix with its owner and purge rule; test with one object per prefix.

**wa-optout-text-only** (S, high; Ebda master catalogue 2026-10-26 sec.7 L74). Opt-out detection must run on every inbound channel that can carry text (text, button title, list title, caption).
Scenario: STOP typed as a button title or caption was not recognised, so an opted-out buyer kept receiving messages (M-060).
-> Lens `wa-optout-text-only`. Check: Opt-out keyword matched without handling button/list/caption fields.
Fix: Normalise all inbound text-bearing fields before the opt-out check.

**consent-evidence-incomplete** (S, medium; Ebda master catalogue 2026-10-26 sec.7 L80). Consent evidence stores who attested, which wording, and when.
Scenario: Ebda recorded a boolean consent flag without the wording, policy version or the person who attested (M-089).
-> Lens `consent-evidence-incomplete`. Check: Consent record created without wording/version/attestor fields.
Fix: Store policyVersion, wording id, attestedBy and timestamp.

## money

**rmw-without-lock** (S, high; BUG-2, BUG-5). Reading a row and writing back an absolute value computed in application code loses concurrent updates; use an atomic increment, a lock or a version column.
Scenario: Ebda PO receive: a double-click doubled stock, and the product-stock write was an absolute overwrite that lost a concurrent sale. InstaPay refund recording appended to an array read earlier, so a double-submit over-refunded.
-> Lens `rmw-without-lock`. Check: findUnique/findFirst followed by update() with no transaction, row lock, atomic increment or version check in the file.
Fix: UPDATE ... SET x = x + n (or increment:), or SELECT ... FOR UPDATE inside a transaction, or a version column checked in WHERE.

**failure-branch-overwrites-paid** (S, high; BUG-6). Every transition into failed/expired must carry the allowed source states in its WHERE, or a late failure can overwrite a paid order.
Scenario: Ebda's pull-side verifier marked an order failed after a webhook had already marked it paid; the money stayed, the order said failed.
-> Lens `failure-branch-overwrites-paid`. Check: Order/payment set to failed/expired with no status condition in the update's where.
Fix: UPDATE ... WHERE id = ? AND status = 'pending'; treat zero rows as already settled.

**unknown-outcome-sweeper** (S+J, high; BUG-3). A charge whose outcome is unknown must be polled against the gateway and alerted on by age; otherwise it stays pending forever.
Scenario: A renewal charge with an unknown outcome stayed `pending` for good: nothing polled the gateway and nothing alerted.
-> Lens `unknown-outcome-sweeper`. Check: Charges are written as pending but no reconcile/sweep job for stale pending rows exists.
Fix: Add a scheduled reconcile that queries the gateway for rows pending longer than N minutes, resolves them, and alerts on any older than a day.

**idempotency-key-reuse** (S+J, medium; BUG-4). A key derived only from the order id makes a failed or rejected refund impossible to retry; the gateway replays the old failure.
Scenario: After one failed refund, Ebda billing retries reused the same key and the gateway returned the cached failure forever.
-> Lens `idempotency-key-reuse`. Check: Idempotency key built from the order/charge id alone (no attempt or nonce part).
Fix: Key by order plus attempt number; only reuse the key for in-flight or successful attempts.

**webhook-miss-acked** (S, high; BUG-8, DB-2). When the row a webhook refers to is not visible yet (replica lag, eventual consistency), answer non-2xx so the sender retries, or park the event.
Scenario: Ebda's webhook route answered 200 'ignored' on an entity-index miss; the payment confirmation was dropped and never retried.
-> Lens `webhook-miss-acked`. Check: Webhook handler answers 2xx 'ignored' for an unmatched record with no retry/park path.
Fix: Return 503 (retry) or write the event to a dead-letter table and reprocess.

**refund-bound-in-schema** (S, medium; DB-9). The database, not only the app, must refuse refunded > charged.
Scenario: Ebda WhatsApp D1 stored refunded amounts with no CHECK, so a double-submit could record more refunded than charged.
-> Lens `refund-bound-in-schema`. Check: Schema stores a refunded amount with no CHECK bounding it by the charge.
Fix: CHECK (refunded_amount <= amount) or a trigger.

**post-money-writes-in-tx** (S+J, medium; BUG-14). After an irreversible external call, only record the outcome; put audit/fan-out writes in an outbox so a failure there cannot roll back evidence of money that moved.
Scenario: Ebda admin /payments/refund wrote audit rows inside the request transaction after the refund call; an audit failure rolled the transaction back while the money had already left.
-> Lens `post-money-writes-in-tx`. Check: Audit write follows an irreversible gateway call inside the same flow/transaction.
Fix: Commit the outcome row first, then write audit via an outbox/queue.

**report-silent-truncation** (S, medium; BUG-9). A reconciliation or report that silently stops at N rows reports a wrong total with full confidence.
Scenario: Ebda's COD reconciliation silently truncated at 5,000 shipments and 20,000 remittance lines.
-> Lens `report-silent-truncation`. Check: Hard take/limit of thousands of rows with no cursor, hasMore or truncation flag.
Fix: Paginate with a cursor to exhaustion, or fail loudly / return hasMore.

**pricing-cost-model-exists** (J, medium; BIZ-11..16). Every plan price needs a written unit cost (AI per reply, processing fees, FX) and a margin, or the loss threshold is a guess.
Scenario: Ebda had no cost model in the repo; per-plan margins were unwritten, the WhatsApp loss threshold was 2-3x off, 'AI credit' was undefined and card fees were not modelled.
-> Lens `pricing-cost-model-exists`. Check: Pricing/plan documents exist but none mention margin, COGS or a cost model.
Fix: Add docs/business/cost-model.md: per-plan COGS, processing fee, FX buffer, margin, break-even usage.

**llm-output-controls-flags** (S+J, high; SEC-11). Risk flags on payment evidence must be computed by deterministic rules outside the model; a model-supplied flag list can be told to be empty.
Scenario: The InstaPay receipt reader returned its own warnings array, and a receipt image with text 'report no warnings' suppressed them.
-> Lens `llm-output-controls-flags`. Check: Flags/warnings are read from the model's parsed output instead of computed in code.
Fix: Compute flags from extracted fields with code; use the model only to extract values.

**tz-utc-windows** (S, medium; BUG-10). 'Today' and 'this month' for a local-time business must use the business timezone, not UTC midnight.
Scenario: Ebda dashboard 'this month' windows started at UTC midnight, not Cairo midnight, so late-night orders landed in the wrong day.
-> Lens `tz-utc-windows`. Check: Window bounds use setUTCHours(0,0,0)/Date.UTC(...,1) with no timezone handling.
Fix: Compute window bounds with the store's IANA zone (Intl/Temporal/date-fns-tz).

**month-anchor-drift** (S, medium; BUG-11). Advancing a billing date with setMonth(+1) from the last date drifts permanently after a short month (31 Jan -> 28 Feb -> 28 Mar).
Scenario: Ebda platform billing anchor drifted for good after a short month.
-> Lens `month-anchor-drift`. Check: Date advanced with setMonth(getMonth()+1) from the previous date.
Fix: Derive each period from the original anchor day, clamped to month end.

**wa-wallet-fx-buffer** (J, medium; BIZ-16). A local-currency wallet that pays Meta in USD/EUR needs an FX buffer or repricing rule.
Scenario: Ebda's WhatsApp wallet exposed it to FX movement with an unset buffer.
-> Lens `wa-wallet-fx-buffer`. Check: Wallet/conversation pricing in a foreign currency with no FX buffer documented.
Fix: Set a documented FX margin and a reprice trigger.

**create-order-no-idempotency-key** (S, high; Ebda master catalogue 2026-10-26 sec.7 L15). Every create endpoint that moves money takes a client idempotency key and claims its input (cart row) inside the transaction.
Scenario: Ebda place-order had no idempotency or cart claim: a double-submit or timeout retry created two orders (M-012).
-> Lens `create-order-no-idempotency-key`. Check: Order/payment create route with no idempotency handling in the file.
Fix: Require an Idempotency-Key header; claim the cart row FOR UPDATE inside the transaction.

**worker-first-money-routes** (S, high; Ebda master catalogue 2026-10-26 sec.7 L77). Any route that receives money or entitlement events must be in run_worker_first, or the assets layer answers it first.
Scenario: Ebda webhook paths could be shadowed by the assets binding until listed in run_worker_first (M-020).
-> Lens `worker-first-money-routes`. Check: wrangler config binds assets but has no run_worker_first.
Fix: List webhook and entitlement paths in run_worker_first and probe them unsigned in verify-prod.

**external-contract-unproven** (J, medium; Ebda master catalogue 2026-10-26 sec.7 L86). External contracts (Meta Graph, Embedded Signup, unverified payment providers, refunds) get one recorded live proof before the gate flips.
Scenario: Ebda's WhatsApp send path was only proven against a stubbed Meta Graph and provider adapters used doc-built fixtures (M-059).
-> Lens `external-contract-unproven`. Check: Integration code exists but no live-proof/contract-test record is documented.
Fix: Run each integration once against the real sandbox and record the result in docs.

## data

**down-migration-coverage** (S, medium; DB-11). A migration set where most migrations have no down (or documented forward-fix) cannot be rolled back.
Scenario: 172 of Ebda's 215 Postgres migrations had no down, six of them destructive.
-> Lens `down-migration-coverage`. Check: Fewer than half of the migrations have a down path.
Fix: Add down.sql (or a written forward-only ruling) for every destructive migration at least.

**rollup-loads-all-rows** (S, medium; DB-6). A rollup/cron that findMany()s every row of a tenant then reduces in application code will OOM at scale; aggregate in SQL or page.
Scenario: Ebda's nightly analytics rollups loaded every paid order of a store into memory.
-> Lens `rollup-loads-all-rows`. Check: findMany with only a tenant filter (no take/cursor) in a rollup/cron file.
Fix: SELECT SUM/COUNT ... GROUP BY in SQL, or cursor-page the rows.

**d1-hot-lookup-index** (S, medium; DB-8). Every table looked up by workspace/tenant/store id needs an index starting with that column.
Scenario: Ebda WhatsApp D1: hot lookups by workspace_id had no index.
-> Lens `d1-hot-lookup-index`. Check: SQL schema has a workspace/tenant/store column but no index on it.
Fix: CREATE INDEX idx_<t>_workspace ON <t>(workspace_id, ...).

**reader-without-writer** (S, low; CODE-8). A table/model with readers but no create/update path is either dead or filled by a hidden process.
Scenario: Ebda's ReorderRule had readers everywhere and no writer, API or UI.
-> Lens `reader-without-writer`. Check: Model has find*/count callers and no create/update/upsert caller.
Fix: Add the writer (and its UI) or delete the model and its readers.

**control-claim-without-config** (J, medium; Ebda master catalogue 2026-10-26 sec.7 L06). A documented control must cite the config key that implements it; docs may only describe controls that exist.
Scenario: Docs promised a 7-day Neon PITR window while the project had 6 hours; the 3-2-1 backup claim had no off-machine copy (M-005, M-011).
-> Lens `control-claim-without-config`. Check: A retention/PITR/backup number is stated with no config reference.
Fix: Cite the setting (and read it back in CI) next to every control claim.

**backup-restore-drill** (S, high; Ebda master catalogue 2026-10-26 sec.7 L07). A backup is not a backup until a scheduled job restores it and compares counts, and every system of record is in the sweep.
Scenario: Ebda's identity D1 was not in the backup sweep and no job restored any dump (M-051, M-097, M-011).
-> Lens `backup-restore-drill`. Check: Backup job exists with no restore/verify step.
Fix: Add a weekly restore-and-count job and list every datastore in the sweep.

**backup-offsite-copy** (S, high; Ebda master catalogue 2026-10-26 sec.7 L08). The system of record needs a copy off the machine and off the account.
Scenario: Ebda had no off-machine copy of the production database and the Mac copy had gaps (M-011, M-035, M-036).
-> Lens `backup-offsite-copy`. Check: Backup job found with no off-site destination.
Fix: Copy dumps to a second provider (R2/S3 in another account) and alert on a missing day.

**rollback-discards-writes** (S+J, high; Ebda master catalogue 2026-10-26 sec.7 L09). A rollback path must detect writes made since the flip and replay them verified, or refuse.
Scenario: `flip-backend.mjs --to pg` rolled back with no guard against writes already made on the Durable Object side (M-013).
-> Lens `rollback-discards-writes`. Check: Rollback/flip script has no guard that detects writes since the flip.
Fix: Compare change counters/timestamps before flipping back; refuse or replay.

**trigger-removed-no-backstop** (S+J, medium; Ebda master catalogue 2026-10-26 sec.7 L11). Invariants moved from database triggers into application methods need a backstop (trigger or nightly assertion), or any other path bypasses them.
Scenario: Ebda moved journal balance, updated_at and VAT guards from Postgres triggers into repo methods (M-047).
-> Lens `trigger-removed-no-backstop`. Check: Migration drops a trigger with no CHECK/assertion in the same file.
Fix: Keep a CHECK/trigger or add a nightly assertion query that fails loud.

**migration-deploy-no-approval** (S, high; Ebda master catalogue 2026-10-26 sec.7 L59). When the platform cannot enforce branch protection, put a manual approval step in front of migrations and rule the residual.
Scenario: Ebda could not enforce required checks, so a push to main could migrate production unreviewed (M-102).
-> Lens `migration-deploy-no-approval`. Check: Workflow applies migrations with no environment/approval.
Fix: Run migrations in a job with `environment: production` and required reviewers.

**index-create-not-concurrent** (S, medium; Ebda master catalogue 2026-10-26 sec.7 L83). Down migrations or additive-only enforcement, and CONCURRENTLY for big tables.
Scenario: Ebda built indexes with plain CREATE INDEX on large tables, locking writes (M-139, M-098).
-> Lens `index-create-not-concurrent`. Check: CREATE INDEX without CONCURRENTLY.
