# money — Money & Transactions Rubric

tags: [BOTH]
sources: PLAYBOOK §3.3 (+ §3.4, foundations table line 41), reference-iceberg-audit.md (terms 9-16: Payments/Billing/Idempotency), the production-grade standard (layer: payments/data), feedback-check-then-set-across-an-await-is-not-atomic (criterion 10), feedback-append-only-event-log-for-money-state (criterion 7), feedback-multi-step-rollback (criteria 12-13); criteria 9-14 distilled 2026-08-17 from msitarzewski/agency-agents `engineering-payments-billing-engineer` (MIT), which surfaced that this rubric graded only internal correctness and never the PSP boundary; criteria 15-16 added 2026-09-04 from a re-read of the same agent (derived idempotency keys) plus the ISO 4217 exponent hazard of the 3-decimal currencies (BHD/OMR/JOD); criterion 17 added 2026-11-12 from the Ebda Store money backfill audit (ebda-store #624: a store-credit return plus a card refund paid one order out twice)

## What "solid" looks like
All money stored and computed in integer minor units (fils/cents), never floats; one tested `money.ts`/`discount.ts` helper centralizing every money calc; money transactions wrapped so `maxWait`/`timeout` are explicit (never the 2s Prisma default); in-transaction idempotency via Postgres `SAVEPOINT` (never bare `create + catch(P2002)`); every multi-match `findFirst` carries a deterministic `orderBy`; and every money/trust state change appends to an event log preserving the raw payload.

And at the **provider boundary**: every inbound webhook is signature-verified over the raw body before it can have any effect; duplicate delivery is a no-op enforced by a DB unique constraint, not by an application-level "already processed?" check; out-of-order delivery cannot regress state; the browser redirect back from the PSP is never treated as confirmation; pending payments are driven to a terminal state by a sweep so a dropped webhook cannot strand an order; and a scheduled reconciliation compares the internal ledger to the provider's settlement report and **alerts** on mismatch. Criteria 1-8 make the money correct inside the system; 9-14 make it correct where the system meets the processor — which is where the money actually is; 15-16 close the two boundary details that a generic payments rubric misses and a single-currency rubric cannot: the idempotency key must be derived rather than random, and the currency exponent must be read rather than assumed to be 2 (some currencies are 3-decimal).

## Criteria
| # | Criterion | Solid (grade 2) | Gap detection | Severity |
|---|---|---|---|---|
| 1 | Integer minor units, no floats | All amounts stored/computed as integer fils/cents; no `Float`/`Decimal`-as-money, no float math on amounts | grep schema for `Float`/`Decimal` on money columns (`amount`, `price`, `total`, `subtotal`); grep code for `parseFloat(`/`* 1.`/`/ 100` on amount vars | Critical |
| 2 | Centralized money helper | One `money.ts`/`discount.ts` module (round, clamp, apply) with unit tests; no ad-hoc money math scattered across handlers | file-exists `**/money.ts` OR `**/discount.ts`; confirm a sibling `*.test`/`*.spec` exists; grep handlers for inline rounding/discount math bypassing it | High |
| 3 | Money tx wrapper with explicit timeouts | Every money `$transaction` goes through a `withMoneyTx`-style wrapper passing `{maxWait:10000, timeout:30000}` — never the 2s default | grep for `$transaction(` and confirm a `maxWait`/`timeout` option or wrapper call; flag any `$transaction` on money paths with no second-arg options object | High |
| 4 | Tx wrapper present in test mocks | When the money-tx wrapper symbol exists, every test mock factory exports it (else mock returns `undefined` → throws at runtime, not at typecheck) | grep test mock/factory files for the wrapper export name; confirm each prisma/service mock that money tests use exposes it | Medium |
| 5 | SAVEPOINT idempotency inside tx | In-transaction idempotency uses a Postgres `SAVEPOINT`; no bare `create(...).catch(P2002)` inside an outer `$transaction` (Postgres aborts the whole tx on the unique violation) | grep for `catch`/`P2002` handling inside a `$transaction(` block lacking a `SAVEPOINT`; confirm a `SAVEPOINT`/`$executeRaw('SAVEPOINT ...')` path exists | Critical |
| 6 | Deterministic orderBy on multi-match reads | Every `findFirst` whose `where` can match multiple rows (notably `OR:`) has an explicit `orderBy` (heap order is non-deterministic and drifts with VACUUM) | grep for `findFirst(` blocks containing `OR:` and assert an `orderBy` key is present in the same call | High |
| 7 | Append-only event log for money/trust state | Each money/trust state machine (payment, order, subscription, payout, loyalty) writes an append-only `<entity>_events` row at every mutation, preserving the raw 3rd-party webhook payload; `entity.status` is current state, events are history | file-exists/grep schema for `*_events` tables (e.g. `payment_events`, `order_events`); confirm an insert-on-mutation path (no UPDATE-in-place of status without a paired event insert) | High |
| 8 | Serializable tx paired with conflict retry | Every `isolationLevel: Serializable` (or high-isolation) tx is wrapped in a bounded retry on P2034 / PG 40001 (backoff + jitter), matched on the error `.code` not `instanceof` (mock-safe) — else transient write-conflicts become user-facing 500s under concurrency | grep for `Serializable` tx without a retry-on-write-conflict wrapper | High |
| 9 | Webhook signature verified before any effect | Every inbound PSP/provider webhook route verifies the provider signature/HMAC over the **raw** body, with a timing-safe compare, and rejects before touching money state. Body must not be JSON-parsed-then-re-serialized for the digest | enumerate inbound webhook routes; for each, confirm a `createHmac`/`timingSafeEqual`/provider-verify call precedes any write; flag routes that mutate money state with no verify call, and any digest computed over a re-serialized body | Critical |
| 10 | Duplicate delivery is a DB-level no-op | The provider's event/payment identifier is persisted under a **unique constraint**, and the handler upserts/looks up against it — so a repeat delivery lands on the same row. An application-level "already processed?" check alone is check-then-act across an await and is not atomic under concurrent redelivery | find the handler's dedup key (whatever it is called — `idempotencyKey`, `externalPaymentId`, `eventId`), then confirm that exact column carries `@unique`/`@@unique` in the schema. **Locate the schema first** (`find . -name schema.prisma -not -path '*/node_modules/*'`) — it is often in `packages/database/`, not next to the API | Critical |
| 11 | Out-of-order deliveries cannot regress state | Webhook handlers drive a state machine with an explicit allowed-transition guard; a late `pending` can never overwrite an already-`paid`/`refunded` row. No unguarded `update({ data: { status } })` on a money entity from a webhook path | grep webhook handlers for status writes and confirm each is gated by a transition check (`canTransition`/`allowedFrom`/switch on current status); flag any direct status assignment | High |
| 12 | The redirect back is not confirmation | The PSP return/callback/success URL never marks an order paid. Only a verified webhook, or a server-side status query to the provider, may advance money state — the browser redirect is attacker-controllable and arrives before settlement | grep return/callback/success route handlers for money-state mutation (`status`, `paidAt`, balance/credit writes); any such write outside a verified-webhook or server-side-verify path is a gap | Critical |
| 13 | Pending payments are driven to a terminal state | A scheduled sweep resolves payments stuck in a non-terminal state past a threshold by querying the provider, so a dropped webhook does not strand an order forever. The sweep is itself idempotent | grep for a cron/queue job selecting non-terminal payment rows older than N minutes and calling a provider status API; absence of any such job is the gap | High |
| 14 | Ledger reconciled against provider settlement | A scheduled reconciliation compares internal money records to the provider's settlement/payout report and **alerts on mismatch** — a silent break is the failure mode. Covers amount, currency, and count, not just presence | grep for a reconciliation job; confirm it compares totals against a provider report and raises an alert (notify/Sentry/Telegram) on non-zero difference, rather than only logging | High |

| 15 | Idempotency keys are DERIVED, not random | The key sent to the PSP is derived from the logical attempt — `order-<id>-attempt-<n>` — so a retry of the same attempt collides on purpose and the provider returns the original result. A fresh `randomUUID()` per retry defeats the entire mechanism: the provider sees a new request and can charge twice. Criterion 5 covers idempotency INSIDE our transaction; this is the key that crosses the boundary | grep for the header/field the PSP expects (`Idempotency-Key`, `idempotencyKey`, the PSP's merchant-reference field) and confirm its value is built from stable identifiers; flag any `randomUUID()`/`uuidv4()`/`Date.now()` feeding it | Critical |
| 16 | Currency exponent is read, never assumed to be 2 | Minor-unit conversion uses the currency's ISO 4217 exponent from a table, not a hardcoded `100`. **Some currencies are 3-decimal** (1 unit = 1000 sub-units): BHD, OMR, JOD, TND and LYD; JPY and KRW are 0-decimal. A `× 100` on a 3-decimal amount is wrong by 10×, and it is wrong in the direction that undercharges. Criterion 1 says "integer fils/cents", which is necessary but not sufficient: the integer has to be in the right unit | grep for literal `100` in money conversion (`* 100`, `/ 100`, `toFixed(2)`, `Math.round(x*100)`) on any path that can carry a non-2-exponent currency; confirm a currency→exponent map exists and is the only source of the multiplier | Critical |
| 17 | One refundable balance, all channels | Every order has ONE refundable balance: what was paid minus every refund through EVERY channel (card/provider, InstaPay or other merchant-recorded transfers, store credit and wallet give-backs, cash/COD returns, merchant-booked amounts). Each refund writer reads that one function and enforces it inside the SAME atomic section as its write (a claim before an external call counts as spent until released). A per-channel cap (payment remaining, return allocation) is necessary but not sufficient: two channels each under their own cap can still pay the order out twice. A refund that already happened outside the system (a provider webhook) is recorded in full and flagged for review, never rejected | enumerate every code path that credits money back to a customer (grep `refund`, `store_credit`, `wallet` credits, `refunded_amount`); for each, confirm it calls the shared balance function inside its transaction; then drive each PAIR of channels against one order in a test and assert the sum never passes the order total. A path with its own private ceiling is the gap | Critical |
