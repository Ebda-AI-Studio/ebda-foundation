# deploy-verify — Deploy-Time Verification Rubric

tags: [BOTH]
sources: feedback-lockfile-regen-must-match-deploy-node-version (criterion 8, a previous storefront product #2524 case), PLAYBOOK §7, CLAUDE.md (rule 15 — pre-push hook mirrors CI subset; rule F — verify against production after every deploy), verify-against-production-after-every-deploy, cursor/plugins pstack verify-this + explain-the-number (verdict set, 2026-10-08), fix-shipped-but-not-live, deploy-and-verification-traps

## What "solid" looks like
Before any push touching deps / build config / migrations / env-var usage / service config, the deploy target's EXACT commands are simulated locally (90s vs ~30-min mean recovery on a failed deploy); lockfile regen matches the deploy target on all four dimensions (Node/npm version, platform, scope, rootDirectory); script-injected plain JS is syntax-checked; and a pre-push hook mirrors the CI subset so failures are caught before burning runner minutes.
**And the verification does not stop at the push.** A merge is not a deploy, a deploy is not a working
feature, and a green suite is evidence about the test environment, never about production. "Is it
deployed?" is answered from the running system, and the changed path is measured live afterwards —
reporting both what was verified AND what could not be, with the reason.

## Ebda procedure (Cloudflare Workers) - run after EVERY merge to main
1. **List every pipeline the merge should have triggered** (path filters differ per workflow; `gh run list --commit <main-tip-sha>`): Workers deploy for api / web / admin / storefront / brain, plus docs, migrations and cron schedules. Each must be COMPLETED + SUCCESS. A cancelled run is a deploy that did not happen and nothing retries it; one green pipeline says nothing about the others.
2. **Compare running commit to main tip**: `curl -s <host>/health` -> `commit` / `deploymentId` vs `git rev-parse origin/main`. `commit: null` is UNKNOWN (use `deploymentId` / `wrangler deployments list`), not failure. A bare 200 is also returned by the previous release.
3. **Measure the changed path live** (a real round-trip, the rendered page in the right locale, read-only SQL, a live response header). Status codes are not evidence of rendering.
4. **Schedules**: after a deploy touching crons, confirm the live schedule list and one tick (Cloudflare cron weekday: 1 = Sunday, 0 is rejected).
5. **Report both halves** with a verdict per claim (criterion 15): VERIFIED (evidence), NOT VERIFIED (reason), INCONCLUSIVE. A report with no "could not verify" section is incomplete. Production writes while verifying stay guest-shaped; never complete a purchase.

## Criteria
| # | Criterion | Solid (grade 2) | Gap detection | Severity |
|---|---|---|---|---|
| 1 | Deploy-target command simulated before risky push | Railway path runs `cd <rootDirectory> && rm -rf node_modules && npm ci --omit=dev`; Vercel path runs `npm ci && npm run build` locally before pushing dep/build/config changes | grep `package.json` scripts / `docs/DEPLOYMENT.md` / pre-push hook for a documented `npm ci --omit=dev` (Node service) or `npm ci && npm run build` (Workers build) simulation step; absent = no local mirror | High |
| 2 | Lockfile pinned to deploy-target Node/npm version | `engines.node` (and npm) declared and matched when regenerating the lockfile | grep `package.json` for an `"engines"` key with a `"node"` field; missing `engines.node` = dimension 1 unverified | High |
| 3 | Lockfile platform-complete (Linux optional deps pinned) | macOS-skipped Linux-only optional deps are explicitly pinned (e.g. `@emnapi/*`) so the Linux deploy doesn't miss them | grep `package.json`/`package-lock.json` for explicit platform-specific optional deps (`@emnapi/`, `@img/`, `lightningcss-linux`, `@next/swc-linux`); macOS-only lockfile lacking the linux variants = drift | High |
| 4 | Lockfile scope correct (prod deps survive `--omit=dev`) | Runtime deps live in `dependencies`, not `devDependencies`, so `npm ci --omit=dev` doesn't drop them | run `npm ci --omit=dev` then check runtime imports resolve; grep for runtime packages misplaced under `devDependencies` | High |
| 5 | Lockfile fixed at the right rootDirectory | The `package.json` regenerated is the one under the deploy service's `rootDirectory` (correct workspace in a monorepo) | compare deploy config `rootDirectory` against the path of the edited `package.json`/lockfile; mismatch = wrong manifest fixed | Medium |
| 6 | Script-injected plain JS syntax-checked | Any hand-written / script-injected plain `.js` is `node -c <file>` checked (typecheck alone misses malformed JS → container crash-loop) | grep build/deploy scripts for a `node -c` (or `node --check`) step over generated/injected JS files; absent = malformed-JS risk uncaught | Medium |
| 7 | Pre-push hook mirrors CI subset | Pre-push hook runs lockfile-drift check + prisma generate + lint + typecheck + unit before the push | file-exists `.husky/pre-push` (or `.git/hooks/pre-push`); grep it for a lockfile-drift/`npm ci`-diff check + lint + typecheck + unit invocation | Medium |
| 8 | Lockfile npm-version pinned to the runner | `engines.npm`/`engines.node` declared = the CI runner's version; CI-bound lockfiles regenerated with `npx npm@<runner-ver> install --package-lock-only` and verified `npm ci --dry-run` exits 0 — local npm vs runner npm resolve different trees → `npm ci` rejects with "Missing: X from lock file" (a previous storefront product #2524: lock written by a newer npm major than CI's Node 20 shipped). Probe: workflow `node-version` majors vs the lockfile's `lockfileVersion` / `packageManager` / `engines`; offline-safe, no network | grep package.json for `engines.npm`/`packageManager`; compare each workflow's `node-version` against `lockfileVersion` (npm 7-8 write v2, npm 9+ v3; Node 18/20 ship npm 9/10) and `packageManager` npm major; flag a mismatch or an undeclared pairing | High |
| 9 | Verify a fix on the branch tip, not the working tree | Before claiming a typecheck/lint/build fix landed, confirm it on the committed branch tip (`git show <branch>:<path>`), and the pre-push hook tsc's the committed tip (stash-isolated), not the dirty working tree — working-tree/conversation state drifts from branch state | review pre-push hook for working-tree tsc without stash isolation | Medium |
| 10 | Deploy identity queryable at runtime | `/health` (or equivalent) returns the running `commit` + `deploymentId`, so "is the merged code live?" is answerable by curl | curl the health endpoint; a 200 alone is returned by the PREVIOUS release too. `commit: null` = the build was not told = UNKNOWN, not failure — verify by `deploymentId` instead | High |
| 11 | Changed path measured against production after deploy | The specific path that changed is exercised or measured live (a real round-trip, a read-only production count, or the rendered page inspected) before "done" is claimed | look for post-deploy evidence in the PR/handoff: status codes are not evidence of rendering; a green CI run is not evidence about prod | High |
| 12 | Unverifiable paths named explicitly | Paths production has never exercised are stated as proven-by-test-only, with the reason | a report claiming blanket verification with no "could not verify" section is incomplete by construction — surfaces with zero production rows (returns, affiliate events, a dark feature) cannot be verified from data | High |
| 13 | Read-only production measurement available before a usage-dependent change | Before shipping a change whose blast radius depends on current usage, that usage is COUNTED, not assumed | is there a query/log filter that counts the surface today? If the answer is "the logger records path only", enforcement would ship blind — that is itself a finding | High |
| 14 | Production writes during verification are proportionate | Guest-shaped writes (creating a cart) are fine — every visitor does them. Completing a purchase is not: it writes a real order, moves inventory and fires merchant notifications | check that verification steps against a CLIENT's live store are read-only or guest-shaped, or were explicitly authorised | Medium |

| 15 | Every verification claim carries a verdict | Each claim is labelled **VERIFIED** (measured live, evidence attached), **NOT VERIFIED** (not checked; reason stated) or **INCONCLUSIVE** (checked but the evidence cannot decide, e.g. p95 measured while requests were failing, or the sample is too small). Measured numbers pass `benchmark-vet` before they are claimed | a "done" report with unlabelled claims, or a latency number without its error rate, sample size and environment, fails | High |
