# auth — Authentication & Authorization Rubric

tags: [BOTH]
sources: PLAYBOOK §3.1, CLAUDE.md (auth rate-limit rule)

## What "solid" looks like
One auth provider per frontend as the sole checker; a uniform middleware chain on every protected route; an ownership guard on every tenant-id endpoint; auth rate-limited; documented JWT lifetime.

## Criteria
| # | Criterion | Solid (grade 2) | Gap detection | Severity |
|---|---|---|---|---|
| 1 | Single auth checker per frontend | One `AuthProvider`; no page re-checks `/auth/me` | grep pages for repeated `/auth/me`/`getSession` calls outside the provider | High |
| 2 | Uniform middleware chain | `authenticate → authorize(roles) → requireResourceAccess → handler` on every protected route; ONE role-check helper name | grep route files for mixed `authorize(`/`requireRole(`; list protected routes missing the chain | Critical |
| 3 | Ownership guard on tenant endpoints | Every endpoint with a tenant/store id param calls the ownership guard; public endpoints do NOT | grep handlers with `:storeId`/`storeId` param lacking `requireStoreAccess`/equivalent | Critical |
| 4 | Auth rate limit | 5 attempts / 15 min / IP+email, Redis-backed | grep login/register/forgot for a rate-limit middleware; confirm Redis store not in-process | High |
| 5 | JWT lifetime documented | Lifetime + stale-role-requires-relogin behavior documented | grep docs/`*.md` for a JWT lifetime statement | Medium |
| 6 | MFA on high-value/admin | TOTP 2FA available + `requireMfaEnrolled` gating ALL admin routers; token revocation (`jti` denylist + `tokenVersion`) | grep for MFA enrol/verify + a revocation check; confirm every admin router is gated | High |
| 7 | No GET consumes a credential or sets a session | Any single-use credential (magic link, invite, confirmation, OAuth-style code) is VERIFIED read-only on GET and CONSUMED on POST; the POST additionally requires exactly `application/json` (415 otherwise) so no HTML form can drive it cross-site | grep routes for a GET handler that writes `used_at`/mints a cookie. Two live failures: `<img src=".../magic?token=…">` logs a victim into the ATTACKER's account — `SameSite=Lax` governs cookie *sending*, not *setting* — and mail scanners/prefetchers burn the link before the human clicks, presenting as "already used". Note this SHARPENS `feedback-csrf-guard-method-aware`: its "safe methods are CSRF-irrelevant" holds only while GET has no side effect | Critical |
| 8 | Removing an exemption names who it was carrying | A diff that deletes an exemption, bypass, allowlist entry or `return next()` from a shared gate ENUMERATES the callers that exemption was serving, by path, in the PR body — not "is the hole closed" alone | Take the deleted condition, list every route it previously admitted, and check each still has a way through. a previous storefront product 2026-09-03: removing the merchant-origin CSRF exemption was correct, but its comment asserted "guest checkout is unaffected: `/public/` paths return early" and `POST /payments/create` is not a `/public/` path. Every guest card payment on a merchant custom domain 403'd for two days — 17 orders, zero payment rows — while the storefront still rendered fine | Critical |
| 9 | A required credential has a mint path reachable by every caller it gates | For any capability a gate makes REQUIRED, the ISSUER's call sites cover every caller class the gate covers — unauthenticated, cookie-session, Bearer | grep the generator, not the verifier. a previous storefront product's `generateCsrfToken` had exactly two callers, both behind authentication, while `csrfProtection` covered unauthenticated storefront routes, so the required token was unobtainable by the callers who needed it. Any claimed self-heal ("client re-mints on 403", "heals on next silent refresh") must be exercised for EACH class named — a role- or client-gated mint silently excludes one | Critical |
| 10 | An admission gate is covered by a probe that walks the real client path | A synthetic check exercises the gate the way a browser does (cookies, CSRF headers, real Origin), and runs on every deploy | Ask which monitor would have caught the last admission regression; if none would, that absence IS the finding. a previous storefront product's checkout monitor probed `/payments/methods` with curl — never carrying cookies or CSRF headers — and stayed green through the whole outage. Prefer an OUTCOME measurement (orders created vs payment rows written) over a liveness probe | High |
| 11 | Post-auth redirect validated against an allowlist | A `returnTo`/`redirect`/`next` parameter driving where the user lands after login is checked against a same-origin-path allowlist before use; encoded/obfuscated variants (double-encoded, backslash, protocol-relative `//evil.com`, control-char prefixes) are rejected by the SAME check, not left to a naive string-startswith test they can slip past | `grep -rniE "req\.(query\|body)\.(returnTo\|redirect\|next\|continue\|redirect_uri)" apps/api/src/routes/auth* apps/web/src/**/login* 2>/dev/null`; a `res.redirect(returnTo)` (or Next `redirect()`) with no scheme/host check feeding it directly is the finding. A login page that just verified the user's real password is the highest-trust moment to abuse for a phishing handoff | Critical |
